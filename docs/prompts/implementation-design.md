# JevPilot 구현 설계 프롬프트

버전 0.1 · 2026-10-06 · 용도: 저장소를 읽을 수 있는 코딩 에이전트에게 **구현 전 설계**를 요청한다.

아래 본문을 작업 프롬프트로 사용한다. 요구사항 명세서와 저장소가 함께 제공되어야 한다. 이는 발표 슬라이드 생성 프롬프트나 UI 디자인 프롬프트가 아니다. 이번 프롬프트의 기본 작업 범위는 조사·설계 문서 작성이며, 코드 수정·유료 API 실행·커밋·push·PR 병합은 별도 지시가 있을 때 수행한다.

---

## 역할과 작업 목표

너는 `RatelXD/JevPilot`의 구현 설계를 맡는다. 현재 코드와 아래 자료를 읽고, 발표 전 완성 가능한 최소 변경 설계를 작성하라. 최신 모델이나 프레임워크를 많이 도입하는 것이 목표가 아니다.

프로젝트의 질문은 다음과 같다.

> LLM-only Computer Use와 비교했을 때, 반복적인 UI 행동 선택을 Jev에 맡기면 작업 성공률을 유지하면서 지연 시간과 API 비용을 줄일 수 있는가?

원안의 역할 분담을 유지하라.

- Frontier LLM: 목표 해석, 고수준 계획, 예외 복구와 재계획.
- Jev: 현재 관측에서 코드가 허용한 후보 중 다음 행동 선택.
- Playwright와 일반 코드: 관측, 후보 구성, 정책·유효성 검사, 실행, 독립적인 성공 판정.
- 자유 문자열: 필요한 입력 단계에서만 LLM이 생성한다. 이 역할은 기존 LLM 연동을 재사용할 수 있고 별도 모델 도입이 필수는 아니다.

정확히 무엇이 현재 구현되어 있는지, 무엇을 새로 설계하는지 분리하라. Mock 실행이나 TODO 클래스가 있다는 이유로 실제 모델 연동이 완료되었다고 쓰지 마라.

## 2. 반드시 지킬 범위

Python + Pydantic + Playwright + 현재 모듈 분리를 유지하라. `browser-use/jev-ultrafast`는 Browser Harness/CDP를 사용하므로 그 실행기를 통째로 이식하지 마라. 별도 React/FastAPI 서버, DB, 분산 큐, 멀티에이전트, 신규 로컬 모델, 학습 파이프라인을 기본 설계에 넣지 마라.

M0는 단일 탭의 일반 HTML/ARIA 컨트롤과 로컬 fixture 중심이다. iframe, shadow DOM, canvas, 업로드, 새 탭, OS 전체 자동화, 로그인된 개인 프로필, 실제 결제·삭제·메시지 전송은 제외한다. Docker·대시보드·공개 사이트 데모·snapshot replay는 M0 이후 항목으로 분리한다.

원안의 3주 계획은 구현 순서의 기준이다. 현재 시점에 3주가 새로 남았다고 가정하지 마라. 시간이 모자라면 겉모습보다 실제 API 연동·다단계 동작·검증·측정을 먼저 완성하는 계획을 제시하라.

## 3. 현재 코드의 간극을 먼저 확인하라

검토 당시 저장소는 Mock 기반 최소 수직 슬라이스였고, 실제 LLM/Jev provider는 미구현이었다. 이 설명을 그대로 믿지 말고 현재 파일을 확인하라. 아래 항목별로 파일/심볼, 현재 동작, 요구사항 ID, 최소 변경, 회귀 위험을 표로 작성하라.

- `PlannerProvider.plan`이 실제로 받는 입력과 실패 근거 전달 가능 여부.
- `DecisionProvider`의 실제 네트워크 연동 및 응답·예외 계약.
- Observer의 사전 지정 selector 의존성, CLICK 외 동작 지원 여부.
- Runtime의 정상 step 반복과 재계획 반복이 분리되어 있는지.
- 낮은 confidence 이후 같은 provider 재호출과 실제 LLM 복구가 구분되는지.
- 최종 성공 판정이 LLM이 만든 조건이 아니라 task의 독립적인 evaluator인지.
- Static/Mock 호출이 실제 LLM 호출로 집계되는지, provider 재사용 시 누적 지표가 섞이는지.
- planner·text·fallback·실패 요청의 시간/비용이 빠지는지.

실행하지 않은 테스트는 미실행이라고 표시하라. 설계 단계에서 유료 API를 호출하지 마라.

## 4. 제안할 아키텍처와 상태 전이

기존 모듈을 확장하는 설계를 기본안으로 제시하라. 책임과 경계를 설명하고, 새 클래스를 추가하는 이유가 단순한 추상화 욕구인지 실제 요구 때문인지 판단하라.

설계에는 다음 경로가 드러나야 한다.

```text
TaskSpec → 초기 상태 → LLM 계획
  → 관측 → 후보 생성 → selector → 응답/정책 검사
  → 필요한 입력값 생성 → 실행 직전 freshness 검사
  → 실행 결과 기록 → 독립 검증
  → 다음 step / 다음 subgoal / 완료 / 재계획 / 중단
```

상태 이름은 제안해도 되지만 최소한 READY, OBSERVING, DECIDING, GENERATING_TEXT, EXECUTING, VERIFYING, REPLANNING과 성공·실패·차단·timeout·불명확 실행의 종료 사유를 구분하라. 전체 상태도와 전이 표를 제시하라. 상태도는 텍스트 또는 Mermaid 소스로 작성하면 된다.

정상적인 step마다 planner를 다시 호출하지 마라. `max_steps`, `max_replans`, 모델 전송 시도, stale 재관측, WAIT, wall-time budget을 구분하라. 현재 화면에서 다음 단계로 진행하는 것과 task 전체 검증 실패를 혼동하지 마라.

원안의 기본 fallback은 LLM 재계획이다. 직접 LLM selector로 한 번 우회하는 기능을 추가하고 싶다면 그것은 별도 제안·추가 실험 조건으로 분리하라. 예산과 trace 없이 복구 경로를 여러 겹 추가하지 마라.

## 5. 동적 Action Space와 Jev 요청 설계

M0 동작 집합은 명세서 §2.3을 따르되, 현재 CLICK 예제에서 단계적으로 확장하는 계획을 작성하라.

한 번의 관측은 snapshot ID와 코드가 관리하는 대상 식별자를 가진다. DOM 전체를 매번 보내지 말고 관련 가시 텍스트·역할·이름·현재 값·사용 가능 상태·현재 subgoal·짧은 이력을 전달한다. 후보는 매 관측마다 갱신하고, 축약 규칙·후보 상한·제외 수를 두 모드에 동일하게 적용하라. 정답을 보고 shortlist를 만들지 마라.

Jev 요청은 같은 snapshot에서 operation과 동작별 target 질문을 묶는 형태로 설계하라. Target 질문은 ‘이 동작을 할 경우 어떤 대상인가’라는 조건부 질문이다. 서로의 응답을 읽는다고 가정하지 마라. 다음 화면이나 검색 결과가 있어야 답할 수 있는 질문은 다음 관측 후에 요청하라.

응답 처리 순서는 operation 검증 → 선택된 operation의 target head 검증 → 현재 후보로 매핑 → 정책·freshness 검사다. 선택되지 않은 target head는 행동을 유발하지 않는다. 동작·대상 조합이 타입상 유효한지뿐 아니라 이번 관측에서 실제로 존재하는지도 확인하라.

Operation confidence와 target confidence를 따로 저장하라. 두 분포를 임의로 곱해 ‘성공 확률’을 만들지 마라. LLM이 출력한 숫자와 Jev confidence를 동일하게 보정된 확률로 비교하지 마라. 제공되지 않은 값은 nullable/unknown으로 설계하고 그때의 provider별 정책을 설명하라.

요청·응답 예시를 한 개씩 제시하되, 확인되지 않은 SDK 함수명·응답 필드는 의사 코드로 표시하라. 모델 ID·API 한도·청구 방식은 추측하지 말고 확인 위치와 검증 작업을 남겨라.

## 6. TextValueProvider와 실행 가드

TYPE_TEXT처럼 자유 문자열이 필요한 경우만 LLM 경로를 사용하라. User Goal에 명시된 값을 코드로 안전하게 재사용하는 단축 경로를 제안할 수 있지만, 두 모드에 같은 정책을 적용하고 모델 호출 절감과 코드 단축을 구분하라. fixture 정답을 실행기나 prompt에 하드코딩하지 마라.

입력값 출력 스키마·타입·빈 값·길이를 검사하라. 텍스트 생성 중 화면이 바뀌면 실행 직전에 다시 확인하라. 생성값 캐시는 처음에는 생략해도 되며, 도입한다면 전체 생성 입력이 일치하는 경우에만 재사용하라.

Playwright locator의 자동 대기가 이전 관측과 현재 대상의 의미가 같음을 보장한다고 가정하지 마라. 동일 문서·실제 관측 대상·역할/이름/값·주변 의미 상태·가림/사용 가능 여부를 어떻게 확인할지 설계하라. 무관한 애니메이션 때문에 항상 결정을 폐기하지 않으면서도 의미가 바뀐 대상을 실행하지 않는 절충을 설명하라. 전역 DOM mutation 횟수만을 최종 가드로 쓰지 마라.

결정은 한 번만 소비한다. 클릭/입력/선택 후 관측이 실패해도 이미 수행한 행동 기록을 지우지 마라. 변형 동작의 실행 여부가 불명확하면 상태 확인 없이 같은 동작을 자동 재시도하지 마라. 단순한 stale 읽기 실패와 uncertain mutation은 다른 오류다.

고정된 sleep만 반복하기보다 제한된 이벤트·조건 기반 대기 방법을 제안하라. 참고 구현의 50ms/200ms 수치를 검증 없이 그대로 확정하지 마라.

## 7. 독립 검증·데이터 계약·실험

명세서 §3.3에 맞춰 최소 Pydantic 계약과 기존 모델의 호환성 변경을 설계하라. 실제 코드가 아니라 필드·타입·불변조건과 간단한 의사 코드로 충분하다.

TaskSpec의 evaluator와 숨은 기대값은 모델이 수정하거나 읽는 대상이 아니다. Planner의 subgoal 조건을 최종 task 정답으로 사용하지 마라. DONE은 검증 요청일 뿐 성공 증거가 아니다. 실제 페이지의 목표 URL·필드값·필터·항목 상태로 검사하라.

주 실험은 `llm_only` 대 `jev_hybrid`다. 초기 상태·후보 생성·실행기·검증기·계획/입력값 생성 정책·예산을 맞춰라. 분기 이후 상태가 달라지는 온라인 실험을 ‘매 step 완전히 동일 입력’이라고 쓰지 마라. Selector 자체에 대한 인과적 비교가 필요하면 동일 snapshot replay를 M1으로 분리하라. 그 결과는 브라우저 완주 성능이 아니다.

전체 task 시간은 초기 상태 준비 이후 첫 planner 호출 직전부터 최종 독립 검증·종료까지다. 시작 준비 시간과 full-run 시간도 별도 기록하라. 참고 구현의 7.073초는 초기 준비와 독립적인 사후 검증이 제외된 다른 측정이므로 동일 선상의 목표로 사용하지 마라.

Planner·selector·text·fallback·재시도별 실제 요청 수·시간·usage·비용을 기록하라. 캐시/Mock/Static 호출은 네트워크 호출과 구분하라. 알 수 없는 비용은 0이 아니다. 실패를 포함한 전체 비용, 검증 성공당 비용, 성공/실패/timeout 수와 시간 분포를 제공하는 결과 스키마를 설계하라.

작업 5~10개 중 우선 fixture 후보와 독립 검증 조건을 제시하라. 제안 반복 수는 명세서에 있으나 확정값으로 꾸미지 마라. 임계값 조정과 최종 평가를 분리하고, 성공률 유지의 해석 기준을 결과 확인 후 유리하게 고르지 마라.

## 8. 보안·범위·출처

허용 origin과 동작 정책은 모델 판단보다 우선한다. 페이지 텍스트의 지시가 goal, 실행 예산, 허용 권한을 바꿀 수 없도록 한다. 비밀번호·쿠키·토큰·개인정보를 모델에 불필요하게 보내거나 공개 trace에 저장하지 마라. 별도 브라우저 context와 합성 테스트 데이터를 기본으로 한다.

후보가 제한되어 있다고 의미적으로 잘못된 선택이나 prompt injection이 사라지는 것은 아니다. 완전한 안전 보장을 주장하지 말고 허용한 작업·지원하지 않는 화면·잔여 위험을 적어라.

`jev-ultrafast`의 Agent는 별도 LLM 고수준 계획과 confidence 기반 planner fallback을 이미 제공하는 코드가 아니다. 이 부분은 JevPilot이 추가로 구현해야 할 설계다. 원본의 DONE 처리와 예제의 독립 검증도 구분해서 설명하라.

기존 자료와 외부 소스에서 확인한 사실, 이번에 제안하는 설계 판단, 확인할 수 없는 정보를 각각 표시하라. 코드를 실제로 재사용한다면 MIT 고지와 원본 경로·commit을 유지하는 방법을 설계에 포함하라. 이번 설계 문서 작성 과정에서 원본 발표자료의 오류·페이지 수·예시 수치를 조용히 고치지 마라.

## 9. 반드시 제출할 설계 결과

아래 순서로 한국어 설계 문서를 작성하라.

1. **현재 구현과 간극 표**: 실제 파일/심볼 → 요구사항 ID → 누락 기능 → 최소 변경.
2. **설계 결정 표**: 채택/비채택, 출처 또는 제안 여부, 이유·대안·일정 영향. Browser Harness 전환·최신 모델 추가를 하지 않는 이유 포함.
3. **컴포넌트와 상태 전이**: 책임 경계, 정상/재계획/stale/불명확 실행/종료 경로, 실제 LLM 호출 지점.
4. **데이터·provider 계약**: 입력/출력/오류/불변조건, 기존 Pydantic 모델과의 변경 관계, Jev 요청 의사 코드.
5. **파일별 구현 계획**: 기존 파일 수정과 꼭 필요한 새 파일만 표로 작성. 새 구조를 과도하게 중첩하지 않음.
6. **수용 테스트 매핑**: FR/NFR → AT → fixture/가짜 응답 → pass 조건. 일반 테스트와 live API 테스트 분리.
7. **평가 계획과 결과 스키마**: 작업·초기화·반복·임계값 검증 분리·측정 경계·비용 누락 방지·실패 보고.
8. **작은 구현 단계와 커밋 계획**: 각 단계의 의존성·완료 조건·검증 명령·되돌리기 방법. 완료하지 않은 명령을 존재한다고 쓰지 않음.
9. **미확정 사항과 결정 필요 항목**: 진행을 막는 것만 질문 후보로 모으고, 나머지는 보완 제안으로 표시.

각 항목은 실제 저장소 파일을 근거로 작성하라. 추상적인 ‘확장성·안정성 강화’로 끝내지 말고, 어느 함수의 어떤 계약을 어떻게 바꿀지 설명하라. FR-01~FR-14와 NFR-01~NFR-08, AT-01~AT-15가 빠짐없이 추적되게 하라.

최종 검토에서 다음을 스스로 확인하라.

- 실제 모델 연동과 Mock을 구분했는가?
- 정상 step마다 planner를 부르는 설계가 아닌가?
- Jev가 생성할 수 없는 자유 문자열·미관측 대상을 생성한다고 가정하지 않았는가?
- 공통 Action Space와 provider별 confidence 의미를 혼동하지 않았는가?
- 거짓 DONE, stale 대상, uncertain mutation, 중복 실행을 다뤘는가?
- planner·text·재시도·실패 비용과 최종 검증 시간을 빠뜨리지 않았는가?
- 기존 3주 계획과 발표 범위에서 끝낼 수 있는가?
- 테스트 통과·성능 향상·원본 파일 업로드를 실제 확인 없이 완료라고 쓰지 않았는가?

설계를 제시한 뒤 멈춰라. 코드 구현이나 외부 변경을 자동으로 시작하지 마라.
