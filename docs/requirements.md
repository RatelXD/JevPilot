## 1. 선정 배경 및 문제 정의

### 1.1 원안에서 유지하는 질문

**LLM-only Computer Use와 비교했을 때, 반복적인 UI 행동 선택을 Jev에 맡기면 작업 성공률을 유지하면서 지연 시간과 API 비용을 줄일 수 있는가?** [S1 §1·§6, S2 p.8·p.13]

범용 모델을 제거하는 것이 아니라 역할을 분리한다. Frontier LLM은 목표 해석·고수준 계획·예외 복구를 담당하고, Jev는 현재 허용된 후보 중 다음 행동을 선택하며, Playwright와 일반 코드는 관측·실행·결과 검증을 담당한다. [S1 §2~§4, S2 p.9~p.11]

이번 산출물은 브라우저 작업을 대상으로 하는 연구용 프로토타입이다. 다른 프로젝트의 처리량·속도·비용을 JevPilot의 성능으로 제시하지 않는다. 개선되지 않은 결과도 연구 질문에 대한 유효한 결과로 기록한다.

### 2.3 행동 계약

M0의 목표 동작은 `CLICK`, `TYPE_TEXT`, `SELECT`, `SCROLL_UP`, `SCROLL_DOWN`, `WAIT`, `DONE`, `BLOCKED`이다. 이는 참고 구현의 동작 집합을 가져온 **설계 제안**이며, 현재 JevPilot에 이미 구현되어 있다는 뜻이 아니다. [S5]

`CLICK`은 클릭 가능한 관측 노드, `TYPE_TEXT`는 수정 가능한 입력 필드, `SELECT`는 관측된 native select의 유효한 옵션만 대상으로 한다. 체크박스·라디오는 M0에서 CLICK과 상태 확인으로 다룬다. WAIT의 시간과 scroll의 크기는 코드 설정으로 제한한다. DONE/BLOCKED는 브라우저 변형 동작이 아니라 제어 신호다.

동작·대상 head의 판단은 같은 상태에 대한 조건부 질문으로 작성한다. 두 출력이 확률적으로 독립이라고 가정하거나 확률을 곱해 ‘행동 성공 확률’을 만들지 않는다. operation confidence와 selected-target confidence를 따로 보관·평가한다. 원본 후보와 응답 간 ID 매핑은 코드가 소유한다. [참고 S5, 확률 처리 조건은 보완]

## 3. 대략적인 동작 원리와 설계 제약

### 3.1 정상 경로

```text
목표 + TaskSpec
  → 초기 브라우저 상태
  → LLM Planner
  → Observer / Action Builder
  → DecisionProvider (LLM 또는 Jev)
  → 응답 검사·실행 정책 검사
  → 필요한 경우 LLM 입력값 생성
  → 실행 직전 freshness 검사
  → Playwright 실행·실행 결과 기록
  → 독립적인 subgoal/전체 결과 검증
  → 다음 행동 / 다음 subgoal / 종료
```

기존 `planner`, `observer`, `decision`, `executor`, `verifier`, `telemetry`, `runtime`의 책임 분리를 유지한다. 새 브라우저 프레임워크·DB·웹 백엔드는 도입을 전제하지 않는다. [S6 + 보완]

### 3.2 예외 경로

| 조건 | 처리 원칙 | 자동 실행 여부 |
| --- | --- | --- |
| 선택 이후 대상 변경, 아직 어떤 변형 동작도 수행하지 않음 | 결정을 폐기하고 제한적으로 재관측·재선택 | 새 판단 전에는 실행하지 않음 |
| 선택 confidence 부족 | 현재 근거와 이유를 전달해 LLM 재계획 | 기존 선택은 실행하지 않음 |
| API 응답 불량·연결 실패·rate limit | 제한된 요청 재시도 또는 명시적 실패/LLM 복구 | 실패 응답으로 실행하지 않음 |
| 클릭·입력·선택 도중 응답이 끊겨 부작용 여부 불명 | `uncertain_execution`으로 기록, 읽기 전용 확인 후 정지 또는 복구 결정 | 같은 변형 동작을 곧바로 재전송하지 않음 |
| 반복 행동에도 진행 없음 | 정체 원인을 포함해 재계획; 예산 소진 시 BLOCKED | 무한 반복 금지 |
| DONE이지만 실제 완료 조건 불충족 | 실패 근거를 남기고 재계획 또는 실패 종료 | 성공으로 집계하지 않음 |
| 허용 도메인 밖 이동·지원하지 않는 UI·위험한 작업 | 중단하고 사유 표시 | confidence와 무관하게 금지 |

위 표의 세부 분기와 상태명은 **보완 제안**이다. 모든 문제를 LLM으로 해결하거나 confidence를 권한 판단에 사용하는 설계는 채택하지 않는다.

### 3.3 최소 데이터 계약 — 필드 수준 제안

| 계약 | 필수적으로 표현할 정보 |
| --- | --- |
| TaskSpec | task_id, goal, initial_url/fixture, allowed_origins, 초기화 방법, evaluator 참조, 예산, 반복/언어 조건 |
| Plan | plan_id, 현재 subgoal, subgoal 목록, 이전 계획과의 연결, 재계획 이유; 모델이 생성한 코드형 evaluator는 금지 |
| Observation | snapshot_id, 문서/내비게이션 식별, URL·제목, 축약된 가시 근거, 컨트롤, 의미 상태 fingerprint, 관측 시각, 제외 후보 수 |
| ActionCandidate | snapshot_id, candidate_id, operation, 코드 내부 target_ref, 이름·역할·현재 상태, 허용 옵션 |
| DecisionInput | goal/subgoal, 허용 규칙, observation, candidates, 제한된 최근 이력; evaluator의 정답·숨은 판정값은 제외 |
| DecisionOutput | snapshot_id, 선택 동작/후보, 선택된 head별 confidence·probabilities, provider·요청/응답 모델 ID, usage, validation 결과 |
| ActionExecution | action_id, decision_id, 수행 시작/끝, executed/failed/uncertain, 오류 유형, 실제 관측 가능한 증거 |
| VerificationResult | subgoal_status, task_status, 검사 항목별 결과, 관측 근거, failure_reason |
| RunTrace / CallEvent | run_id, mode, 설정·코드 hash, 실제 호출별 역할·재시도·시간·사용량·비용, 전이 이력, 종료 사유 |

필드명 자체는 확정 API가 아니다. 구현 설계에서 기존 Pydantic 모델과의 매핑·마이그레이션·테스트를 제시한다. URL·쿠키·개인정보는 모델 입력과 영구 로그에 필요한 최소한만 포함한다.

### 3.4 신뢰도와 완료 판정

임계값은 모델·질문 유형·후보 구성·작업군에 따라 검증한다. 현재 코드의 `0.7`이나 외부 글의 예시 수치를 성공률·안전성 보증으로 삼지 않는다. 서로 다른 primitive의 수치를 동일 기준으로 옮기지 않는다. 임계값을 고르는 작업과 최종 평가 작업을 분리한다. [S4 + 보완]

LLM이 자연어로 생성한 confidence 숫자를 Jev의 확률 기반 지표와 동등하게 취급하지 않는다. 제공되지 않은 confidence는 출처와 함께 unknown/null로 표현하고, provider별 불확실성 정책을 명시한다. 공통 데이터 구조가 공통 확률 보정을 의미하지는 않는다. [보완]

TaskSpec의 최종 evaluator는 사람이 정의한 결정적 검사 또는 허용된 검사 함수로 제공한다. Planner가 제안하는 subgoal 조건과 별개다. 모델이 평가 함수나 기대 정답을 바꿔 성공하도록 만들 수 없어야 한다. 모델 출력의 구조 유효성과 선택의 정답 여부, 실제 실행 여부는 서로 다른 검사다. [S5 + 보완]

## 4. 오픈소스 및 기술 활용

| 구성 | 유지 또는 제안 | 제한 |
| --- | --- | --- |
| Python / Pydantic / pytest | 기존 `pyproject.toml` 유지 | 새 도구를 이미 설치된 것처럼 안내하지 않음 |
| Playwright / Chromium | 기존 실행기 유지, 관측·실행 가드 보완 | Browser Harness/CDP 코드를 그대로 붙여 교체하지 않음 |

| Jev provider | 실제 API/SDK 계약을 확인한 adapter | 코드의 `jev-default`를 검증된 모델 ID로 간주하지 않음 |
| `jev-ultrafast` | 동적 action space, 묶음 질문, text helper, stale/중복 실행 방지, 검증 패턴 참고 | 고수준 planner·confidence fallback을 이미 제공한다고 설명하지 않음 |

API key는 기존 `.env.example` 명명 체계를 우선한다. `.env` 자동 로딩은 현재 보장되어 있지 않으므로, 환경변수 주입 또는 실제로 구현한 로딩 방법을 명시한다. 호출 가능한 버전 ID·실제 응답 ID·SDK 버전을 기록하고, 별칭만으로 실험을 고정했다고 주장하지 않는다. 원본 제안서의 Early Access·가격·속도 표시는 작성 당시 설명으로 보존한다. [S1/S6 + 보완]

이번 문서는 외부 소스의 코드를 복사하지 않는다. 추후 코드 일부를 재사용하면 S5의 MIT 고지, 출처 경로, 사용 commit을 함께 유지한다. 라이선스 확인과 재사용 범위 기록을 구현 검토 항목으로 둔다.

### 5.2 비교 설계

**주 평가: 온라인 end-to-end 비교.** 같은 작업·초기화 규칙·후보 생성·실행기·검증기·계획/입력값 생성 정책에서 selector 경로를 교체한다. 두 모드의 반복 횟수와 총 예산을 동일하게 둔다. 교대로 실행하거나 순서를 기록해 캐시·네트워크·시간대 영향을 드러낸다. [S1/S6, 구체화는 보완]

서로 다른 행동을 선택하면 이후 페이지 상태가 달라질 수 있다. 따라서 온라인 결과를 ‘모든 단계에서 완전히 같은 입력을 받은 selector의 성능’이라고 단정하지 않는다. Planner 출력·복구 횟수도 달라질 수 있으므로 전체 시스템 비교임을 명시한다.

**M1 분리 평가: snapshot replay.** 저장된 동일한 observation·candidates·plan context를 두 selector에 제공해 선택 정답률·지연을 비교한다. 이때 브라우저를 실제 완주하지 않았으므로 작업 성공률로 보고하지 않는다. 기존 공통 Action Space ADR의 통제 취지를 보완하는 별도 실험이며, ADR을 조용히 변경하지 않는다.

초기 평가 크기는 **5개 작업 × 모드별 5회 = 50회**를 제안한다. 이는 원안의 5~10개 작업 중 시작 구성이며 확정된 표본 수가 아니다. 소표본 결과는 탐색 결과로 보고하고, ‘성공률 유지’의 허용 차이·신뢰구간·검정 방법은 결과를 본 뒤 유리하게 선택하지 않는다. 숫자 기준을 확정하지 못하면 관측 차이와 한계를 그대로 제시한다.

### 5.3 작업 후보 — 아직 구현되지 않은 fixture 제안

| 작업 | 목표 / 독립 검증 | 구분 |
| --- | --- | --- |
| T-01 검색·상세 이동 | 목표 항목 검색 후 올바른 상세 URL과 항목 ID 확인 | 기본 CLICK·TYPE_TEXT |
| T-02 필터·옵션 선택 | 원하는 옵션과 복수 필터 적용 후 선택값·결과 항목 확인 | SELECT·체크박스 |
| T-03 다단계 폼 | 합성 정보 입력 후 로컬 결과 페이지의 필드값 확인 | 문자열 생성·subgoal 전환 |
| T-04 지연된 자동완성 | 늦게 나타나는 후보 중 목표 항목 선택, 입력값·선택 ID 확인 | WAIT·재관측 |
| T-05 변경된 대상·잘못된 DONE | 클릭 전 노드 교체/overlay와 미완료 화면을 별도 사례로 제공 | stale·실패 처리·독립 검증 |

T-05의 통제된 정지 사례는 양쪽 모드에 동일하게 제공하고 ‘완주 성공’과 ‘가드가 올바르게 거절함’을 별도 지표로 보고한다. 숨겨진 evaluator 정답·정답 selector는 모델 입력에 전달하지 않는다.

### 5.4 지표 정의

| 지표 | 정의 |
| --- | --- |
| task_success_rate | 최종 evaluator 성공 실행 수 / 시작한 전체 평가 실행 수. timeout·실패를 분모에서 빼지 않는다 |
| task_e2e_ms | 초기 페이지 준비 완료 후 첫 planner 호출 직전부터 최종 독립 검증·종료 기록까지의 wall time |
| startup_ms / full_run_ms | context 생성·초기 탐색 시간 및 그것까지 포함한 전체 시간. task_e2e와 따로 제공 |
| 단계 시간 | planner, observe, decision, text, validate/execute, wait, verify, replan 구간의 별도 시간. 겹치는 구간을 무조건 더해 총시간으로 삼지 않는다 |
| 모델 호출 | 실제 전송 시도마다 역할·provider·성공/실패·재시도를 기록. frontier 호출, 전체 생성형 LLM 호출, Jev 호출을 분리 |
| total_model_cost | planner + selector + text + fallback + 재시도 비용. 청구값/usage 기반 추정값/unknown을 구분 |
| cost_per_verified_success | 실패를 포함한 전체 모델 비용 / 검증 성공 수. 성공 0이면 정의 불가로 표시 |
| fallback·stale·정체 | 원인별 건수와 비율. 원인들의 합을 단일 의미의 성공 실패로 치환하지 않는다 |

성공 실행의 시간 중앙값은 표본 수와 함께 보여주며, 실패·timeout의 시간과 전체 시도 분포도 별도로 제공한다. ‘무료 출력’은 요청 전체 비용이 0이라는 뜻이 아니다. Browser 인프라 비용을 제외했다면 그 사실을 명시한다. 참고 구현의 7.073초와 JevPilot의 측정 경계가 다르므로 직접 속도 순위로 비교하지 않는다. [S5 `performance.md`, 지표 정의는 보완]

## 6. 3주 구현 계획과 완료 기준

원안의 3주 계획을 유지하되, 다음은 그 순서에 맞춘 구현 묶음이다. 지금부터 새로 3주가 확보되었다는 의미는 아니다. [S1 §5]

| --- | --- | --- |
| 1주: Baseline·Provider/Mock | 기존 계약 확인 → 동적 observer → 다단계 runtime → 실제 LLM-only → 기본 trace | 고정된 fixture를 반복 실행하고 독립 검증 결과를 남김 |

## 7. 기대 결과와 미확정 사항

완료 산출물은 실행 가능한 baseline/hybrid, 로컬 과제 정의, 일반/실제 API 테스트의 분리, 재현 가능한 로그·비교 결과, 데모·README다. ‘몇 배 빠름’은 산출물의 합격 조건이 아니다. [S1 §6]
